# Rook audit, 2026-09-29

Read-only review by Codex CLI of Rook end to end. Findings are tracked on the Kaneo RAM board; this is the evidence behind those cards.

1. Cross-account conversation leakage in All inboxes

What goes wrong: Rook chooses the open message’s account correctly, but it keeps the existing transcript and previously allowed message IDs when the user moves to another account. The next model request can therefore contain conversation or tool results from the previous account. If two accounts happen to use the same message ID, the stale allow-list can also authorize an action without a search in the new account. `rookAccount` is overwritten, while `said` and `chatShown` are cleared only by the Clear button.

Evidence: [Main.kt:840](../../src/main/kotlin/org/rampart/Main.kt:840), [Main.kt:3600](../../src/main/kotlin/org/rampart/Main.kt:3600), [Main.kt:3609](../../src/main/kotlin/org/rampart/Main.kt:3609), [Main.kt:3657](../../src/main/kotlin/org/rampart/Main.kt:3657), [Main.kt:5398](../../src/main/kotlin/org/rampart/Main.kt:5398)

Fix: Keep a separate conversation and allowed-ID set per account, or automatically clear both whenever the selected account differs from `rookAccount`.

2. Prompt injection can cause mailbox changes without confirmation

What goes wrong: Archive, Trash, mark read, and tag execute immediately. The only protection against an email saying “archive everything” is a system-prompt instruction. After reading a malicious message, the model can search for messages and act on the returned IDs in later tool rounds. There is no card or programmatic check that the action came from the person rather than message text.

Evidence: [Chat.kt:21](../../src/main/kotlin/org/rampart/Chat.kt:21), [Chat.kt:102](../../src/main/kotlin/org/rampart/Chat.kt:102), [Chat.kt:275](../../src/main/kotlin/org/rampart/Chat.kt:275), [Chat.kt:282](../../src/main/kotlin/org/rampart/Chat.kt:282), [Main.kt:3526](../../src/main/kotlin/org/rampart/Main.kt:3526), [Main.kt:3545](../../src/main/kotlin/org/rampart/Main.kt:3545)

Fix: Put every mutating mail action on a confirmation card, preferably grouping up to 25 messages and showing subjects and accounts. At minimum, require explicit user authorization for the exact action and IDs in the current user turn.

3. The open message bypasses the stated search-only ID rule

What goes wrong: The prompt says actions may use only IDs returned by a search, but the open message is added directly to `chatShown`. Rook therefore sees its ID and may archive, trash, tag, mark, or draft against it without ever searching. This contradicts both the prompt and the documented security boundary.

Evidence: [Chat.kt:103](../../src/main/kotlin/org/rampart/Chat.kt:103), [Chat.kt:148](../../src/main/kotlin/org/rampart/Chat.kt:148), [Main.kt:3621](../../src/main/kotlin/org/rampart/Main.kt:3621), [Main.kt:3625](../../src/main/kotlin/org/rampart/Main.kt:3625)

Fix: Either require an actual search before any mutation, or explicitly define the user-opened message as a separate trusted source and restrict that exception to the one open ID.

4. Common model tool-call formats appear as raw JSON

What goes wrong:

- Prose followed by a final one-line JSON object works.
- One bare or wholly fenced JSON object works.
- Several JSON calls in one reply fail parsing and the complete reply, including JSON, is displayed as assistant prose.
- JSON in a code fence after prose fails because the last nonblank line is the closing fence, so the raw fenced call is displayed.
- A JSON call in the middle of a reply is deliberately treated as prose.
- An invented tool name is parsed, hidden from the UI, then answered with “There is no tool called...”.
- Only one tool can run per model reply.

Evidence: [Chat.kt:111](../../src/main/kotlin/org/rampart/Chat.kt:111), [Chat.kt:120](../../src/main/kotlin/org/rampart/Chat.kt:120), [Chat.kt:131](../../src/main/kotlin/org/rampart/Chat.kt:131), [Chat.kt:135](../../src/main/kotlin/org/rampart/Chat.kt:135), [Chat.kt:219](../../src/main/kotlin/org/rampart/Chat.kt:219), [Chat.kt:302](../../src/main/kotlin/org/rampart/Chat.kt:302), [ChatPane.kt:159](../../src/main/kotlin/org/rampart/ChatPane.kt:159)

Fix: Extract and validate exactly one fenced or bare tool object wherever it occurs, while preserving surrounding prose. If multiple calls are returned, either execute a validated array sequentially or show a friendly request to try again, never raw protocol JSON.

5. Wrong argument types can produce internal-looking errors or silent no-ops

What goes wrong: Many arguments are accessed with `jsonPrimitive`, which throws when the model supplies an object or array. The outer handler then displays the exception’s own message, which is not guaranteed to be a readable sentence. Other type errors silently default: a string instead of an `ids` array becomes an empty list, a malformed Boolean takes the fallback, and a malformed limit becomes 20. A user may see “Archived 0 messages” instead of learning that the call was malformed.

Evidence: [Chat.kt:246](../../src/main/kotlin/org/rampart/Chat.kt:246), [Chat.kt:251](../../src/main/kotlin/org/rampart/Chat.kt:251), [Chat.kt:253](../../src/main/kotlin/org/rampart/Chat.kt:253), [Chat.kt:257](../../src/main/kotlin/org/rampart/Chat.kt:257), [Main.kt:3671](../../src/main/kotlin/org/rampart/Main.kt:3671)

Fix: Give every tool a strict argument decoder that returns a plain-English validation error. Do not execute when a required argument is missing or has the wrong type.

6. Context is character-bounded, but not token-budgeted

What goes wrong: The open message is cut to 6,000 characters and a message read by a tool is cut to 24,000 characters, so huge HTML does not go through whole. However, up to 16 history entries are resent, and several read results can each be 24,000 characters. The long system prompt, file context, open message, and history are combined without considering the selected model’s context limit. Smaller local models can reject the request or lose the useful end through provider-side truncation.

Evidence: [Chat.kt:53](../../src/main/kotlin/org/rampart/Chat.kt:53), [Chat.kt:56](../../src/main/kotlin/org/rampart/Chat.kt:56), [Chat.kt:70](../../src/main/kotlin/org/rampart/Chat.kt:70), [Chat.kt:152](../../src/main/kotlin/org/rampart/Chat.kt:152), [Chat.kt:271](../../src/main/kotlin/org/rampart/Chat.kt:271), [Summarise.kt:66](../../src/main/kotlin/org/rampart/Summarise.kt:66), [Llm.kt:66](../../src/main/kotlin/org/rampart/Llm.kt:66)

Fix: Add a configurable input-token budget and trim or summarize tool results before packet construction. Reserve space for the system prompt, current user question, and output.

7. Visible history grows forever even though model history is capped

What goes wrong: Only the last 16 entries are sent to the model, but the Compose state and transcript keep every prior entry until Clear is pressed. A long-lived Rook panel steadily accumulates UI objects and may become slow. It also creates a comprehension mismatch because the user can refer to something still visible that the model no longer receives.

Evidence: [Chat.kt:47](../../src/main/kotlin/org/rampart/Chat.kt:47), [Chat.kt:152](../../src/main/kotlin/org/rampart/Chat.kt:152), [Main.kt:822](../../src/main/kotlin/org/rampart/Main.kt:822), [Main.kt:3609](../../src/main/kotlin/org/rampart/Main.kt:3609), [Main.kt:3673](../../src/main/kotlin/org/rampart/Main.kt:3673)

Fix: Bound the displayed transcript too, or insert a visible “earlier context forgotten” divider and archive older entries outside active Compose state.

8. Four tool rounds are often too few for the required workflow

What goes wrong: A safe settings change commonly needs `list_settings`, `get_setting`, an explanatory turn, and `change_setting`. Mail work may require search, read, a pre-action announcement, and an action. Any correction or unknown tool consumes the remaining budget. At the limit, the user receives “That went round in circles, so it stopped,” even when the model was making reasonable progress.

Evidence: [Chat.kt:191](../../src/main/kotlin/org/rampart/Chat.kt:191), [Chat.kt:194](../../src/main/kotlin/org/rampart/Chat.kt:194), [Chat.kt:214](../../src/main/kotlin/org/rampart/Chat.kt:214), [Chat.kt:227](../../src/main/kotlin/org/rampart/Chat.kt:227), [RookChanges.kt:299](../../src/main/kotlin/org/rampart/RookChanges.kt:299)

Fix: Count successful mutating calls separately from read-only discovery, or raise the total while detecting repeated identical calls. The exhaustion message should say what completed and ask the user whether to continue.

9. Completed and dismissed cards never leave the panel

What goes wrong: Confirmed, failed, and dismissed setting cards remain in `cards` and continue rendering until the whole conversation is cleared. Filter cards behave the same way. “Leave it” therefore looks more like changing the card’s caption than dismissing it, and old cards crowd out the conversation.

Evidence: [RookChanges.kt:77](../../src/main/kotlin/org/rampart/RookChanges.kt:77), [RookChanges.kt:82](../../src/main/kotlin/org/rampart/RookChanges.kt:82), [RookChanges.kt:87](../../src/main/kotlin/org/rampart/RookChanges.kt:87), [ChatPane.kt:166](../../src/main/kotlin/org/rampart/ChatPane.kt:166), [SettingChangeCard.kt:62](../../src/main/kotlin/org/rampart/SettingChangeCard.kt:62)

Fix: Remove dismissed cards immediately and collapse completed or failed cards into a compact transcript receipt after a short interval.

10. The prompt’s mutation announcement rule is not enforced

What goes wrong: The prompt says Rook must announce a change in the turn before the tool call, but the parser also supports prose immediately followed by a call and executes it at once. A model can also return a bare mutation call. The user never gets a real chance to react to the announcement.

Evidence: [Chat.kt:79](../../src/main/kotlin/org/rampart/Chat.kt:79), [Chat.kt:107](../../src/main/kotlin/org/rampart/Chat.kt:107), [Chat.kt:123](../../src/main/kotlin/org/rampart/Chat.kt:123), [Chat.kt:223](../../src/main/kotlin/org/rampart/Chat.kt:223)

Fix: Track proposed mutation intent in application state and require the next user turn to approve it, or replace the rule with confirmation cards.

The provider error path is comparatively good. HTTP 401 or 403, 429, bad model names, connection failures, and the 120-second timeout are converted to readable sentences, and the request spinner is cleared after the result returns. Evidence: [Llm.kt:98](../../src/main/kotlin/org/rampart/Llm.kt:98), [Llm.kt:127](../../src/main/kotlin/org/rampart/Llm.kt:127), [Llm.kt:138](../../src/main/kotlin/org/rampart/Llm.kt:138), [Main.kt:3671](../../src/main/kotlin/org/rampart/Main.kt:3671), [Main.kt:3683](../../src/main/kotlin/org/rampart/Main.kt:3683). The text field and Ask button are disabled while a request is running, so sending a second request in flight is prevented: [ChatPane.kt:225](../../src/main/kotlin/org/rampart/ChatPane.kt:225), [ChatPane.kt:246](../../src/main/kotlin/org/rampart/ChatPane.kt:246).

All implemented chat tool families are documented once the appended settings, calendar, and task prompts are included. The main prompt documents mail, tracking, and filter tools; the appended prompts document settings, calendar, and tasks. Evidence: [Chat.kt:82](../../src/main/kotlin/org/rampart/Chat.kt:82), [RookChanges.kt:284](../../src/main/kotlin/org/rampart/RookChanges.kt:284), [CalendarTools.kt:40](../../src/main/kotlin/org/rampart/CalendarTools.kt:40), [TaskFromMail.kt:547](../../src/main/kotlin/org/rampart/TaskFromMail.kt:547), [Main.kt:3652](../../src/main/kotlin/org/rampart/Main.kt:3652).

Top 3 improvements:

1. Put archive, Trash, mark-read, and tag operations behind confirmation cards with account and message details.
2. Make conversation history and allowed IDs account-scoped, clearing or switching them automatically in All inboxes.
3. Replace the ad hoc JSON parser with strict, provider-tolerant tool-call extraction and typed argument validation.
